# 一、项目目标

开发一款具有以下能力的微信小游戏：

1. 四名玩家进入同一房间进行实时对局。
2. 支持每人 13 张牌、大小王作为癞子的泸州跑得快规则。
3. 支持合法牌型识别、大小比较、癞子组合搜索。
4. 支持强制出牌、无牌自动跳过以及多圈持续出牌。
5. 支持手牌高亮、不可出牌置灰、点击提示循环展示合法组合。
6. 支持赢家首出限制、炸弹计分、整局结算。
7. 支持 WebSocket 实时同步、断线重连和房间状态恢复。
8. 前后端使用统一的规则定义，避免界面展示结果与服务端校验不一致。

第一阶段以可运行的 MVP 为目标，不要求一开始就实现商城、充值、排行榜、俱乐部等非核心功能。

游戏仅实现娱乐性积分，不实现现金下注、现金兑换或其他现金赌博功能。

# 四、游戏基础规则

以下规则已经由产品需求方确认，属于必须遵守的规则，不允许擅自修改。

## 4.1 人数与发牌

- 四名玩家。
- 使用包含大小王的 54 张扑克牌。
- 每名玩家发 13 张。
- 剩余 2 张牌弃置，不进入任何玩家的手牌。
- 大王和小王都是癞子。
- 洗牌、发牌、首出玩家确定必须在服务端完成。
- 不能由客户端自行决定发牌结果。

## 4.2 首局首出

首局由持有黑桃 3 的玩家先出。

首手出牌必须包含实体牌黑桃 3。

黑桃 3 可以作为单张打出，也可以参与符合牌型规则的其他合法组合。

不能只检查组合中是否存在逻辑上代表黑桃 3 的癞子；必须确认实际包含黑桃 3 这张实体牌。

## 4.3 后续每局首出

后续每局由上一局赢家首先领出。

赢家可以自由选择合法牌型，但首手不得出现以下情况：

1. 单出 2。
2. 单出癞子。
3. 出对子 22。
4. 使用一张自然 2 和一张癞子（癞子当作 2）组成对子 22。

这些限制仅作用于后续每局赢家的首次领出。

不要擅自扩展为禁止所有包含 2 的顺子、连对、飞机或其他组合。

# 五、完整牌型与比较规则

实现牌型识别、合法组合枚举、大小比较和癞子处理时，必须遵循以下规则。

## 5.1 基础牌型

支持：

- 单张。
- 对子。
- 三不带。
- 三带散。
- 三带对。
- 顺子。
- 连对。
- 飞机。
- 炸弹。

不支持四带牌型。四张相同点数的牌按炸弹处理，不额外定义四带二、四带三等牌型。

## 5.2 三张及三带

三不带由三张相同点数的牌组成。

三带散由三张相同点数的牌加两张散牌组成。两张散牌不能组成对子。

三带对由三张相同点数的牌加一个对子组成。

普通牌型响应必须保持牌型一致：

- 三不带只能由三不带响应。
- 三带散只能由三带散响应。
- 三带对只能由三带对响应。

炸弹属于特殊压制牌型，可以压制普通牌型，具体遵循后文的炸弹规则。

对于普通响应，必须校验主体点数、牌型结构以及对应的大小比较规则。不要允许不同长度或不同结构的组合随意互相比较。

## 5.3 顺子

顺子至少包含 5 张牌。

已经确认的最小顺子为：

- A-2-3-4-5，即 12345。
- 2-3-4-5-6，即 23456。
- 3-4-5-6-7，即 34567。

这些示例代表从小到大的顺序。

不能简单地使用普通扑克中 A 永远大于 2 的点数比较规则判断顺子。

顺子比较必须独立实现，并明确区分牌型识别、连续性判断和大小比较。

## 5.4 连对

最小连对为 AA-22，其次为 22-33，再到 33-44，依此类推。

连对必须支持癞子参与组成合法对子。

比较连对时，应校验牌型长度及连续对子主体，不允许不同长度的连对随意互相压制。

## 5.5 飞机

飞机由连续的三张组合构成。

以 333444 为例：

- 飞机不带：333444。
- 飞机带散：333444 加 4 张不同的散牌。
- 飞机带对：333444 加两对。

禁止混合附件形式，例如 333444 加一对和两张散牌。

如果飞机主体由 n 组连续三张组成：

- 飞机不带：3n 张主体牌。
- 飞机带散：3n 张主体牌加 2n 张符合散牌定义的附件。
- 飞机带对：3n 张主体牌加 n 个对子。

飞机主体必须连续，附件结构必须一致。

已经确认的飞机大小示例：

- AAA222 为最小。
- 222333 其次。

注意：需求方曾提到飞机不带可出现 333444555，并提到 666。单独的 666 按通常牌型定义属于三不带，不是连续三组构成的标准飞机。不得擅自将 666 认定为飞机。请在 docs/open-questions.md 中记录这一点，保留独立的规则扩展点。

不同长度的飞机、附件的大小比较，以及更完整的连续区间边界，如需求中未明确，必须隔离为可配置规则或待确认项，不允许直接把未经确认的规则写死。

## 5.6 炸弹

炸弹可以压制普通牌型。

但是：

**手中存在炸弹，不代表必须出炸弹。**

只要存在合法压制方案，玩家必须出牌，但可以从所有合法压制方案中自由选择，包括普通牌型和炸弹。

例如，上家出单张 A，下家有自然 2、一张癞子和三张 K，在符合牌型规则的情况下，可以选择：

- 出自然 2。
- 将癞子当作 2 单出。
- 使用 KKK 加癞子组成合法炸弹。

炸弹不能因为自身特殊而获得强制优先权。

炸弹的完整构成、炸弹张数范围、不同炸弹之间的比较，以及癞子炸弹的特殊大小规则，若没有明确依据，不允许擅自定义。请在规则实现中设置独立的 BombPolicy，并将未确认的细则列入 open-questions.md。

# 六、癞子规则与组合枚举

这是本项目的核心难点之一。

大小王必须参与所有合法牌型的组合搜索，包括：

- 单张。
- 对子。
- 三不带。
- 三带散。
- 三带对。
- 顺子。
- 连对。
- 飞机。
- 炸弹。

不能只枚举天然牌组成的组合，也不能在识别牌型时忽略癞子。

## 6.1 区分实体牌与逻辑牌

每张实体牌必须有稳定且唯一的 ID。

癞子参与组合时，必须分别保存：

1. 实际持有的实体牌。
2. 癞子在当前组合中代表的逻辑身份。
3. 最终识别出的牌型。
4. 对应牌型的比较值。
5. 该组合的合法性依据。

例如，实体小王在一个组合中代表 2，在另一个组合中代表 K，必须能明确追溯原始实体牌。

不能只把小王直接修改成数字 2 或 K，否则可能导致手牌移除错误、组合重复或错误出牌。

## 6.2 组合枚举器

实现独立的 CardCombinationFinder，负责枚举当前手牌中所有符合规则的候选组合。

至少支持以下能力：

- 枚举自然牌组合。
- 枚举包含一张或多张癞子的组合。
- 校验癞子的替代方式。
- 校验首出限制。
- 校验普通牌型与炸弹之间的压制关系。
- 对候选组合去重。
- 输出稳定、可复现的组合结果。

不要简单地枚举 13 张牌的所有子集后再做大量无效计算。应先按牌型结构、点数分组和长度约束进行剪枝。

但在正确性尚未通过测试之前，不要为了性能过早引入复杂优化。

癞子能否任意替代点数与花色、能否参与所有炸弹、多个癞子的具体限制，仍属于需要明确的规则。请实现 WildcardPolicy 接口，并为未确认规则提供明确的占位实现和测试，不允许在代码中到处散落隐式假设。

# 七、强制出牌规则

这是必须严格遵守的规则。

## 7.1 有合法压制组合时

只要玩家手里存在至少一种合法的压制组合，就必须出牌。

但玩家可以自由选择任意一种合法压制组合。

例如：

- 普通牌型和炸弹都能压制：两者均可选择。
- 存在多个普通压制组合：可以选择任意一种。
- 存在多个炸弹：可以选择任意一个合法压制炸弹。

不允许因为玩家有炸弹，就强制要求出炸弹。

不允许因为玩家已经在本轮出过牌，就跳过他的后续行动。

## 7.2 没有合法压制组合时

如果当前玩家不存在任何合法压制组合，服务端自动跳过。

不需要玩家点击“不要”或“过”。

前端也不能要求玩家确认自动跳过。

## 7.3 服务端必须重新验证

前端的手牌高亮只是交互提示，不构成合法性依据。

服务端收到出牌请求后，必须重新检查：

- 玩家是否轮到出牌。
- 提交的实体牌是否属于该玩家。
- 牌型是否合法。
- 癞子使用是否合法。
- 是否能够压制当前桌面牌型。
- 是否符合首出限制。
- 是否违反强制出牌规则。
- 当前房间状态版本是否仍然有效。

如果不合法，拒绝该操作并返回明确错误码。

# 八、一轮定义：必须支持多圈循环

这部分必须严格按照以下定义实现。

一轮不是“首出玩家出牌，然后其他三人各响应一次”。

首出玩家只获得先手机会。

假设玩家顺序为 1 → 2 → 3 → 4：

1. 玩家 1 首先出牌。
2. 玩家 2、3、4 依次检查是否存在合法压制组合。
3. 只要有人成功出牌，当前桌面牌型就更新。
4. 下一位玩家必须针对最新桌面牌型重新计算合法压制组合。
5. 当顺序再次轮到玩家 1 时，如果他有合法压制组合，必须继续出牌。
6. 玩家 1、2、3、4 可以反复循环多圈。
7. 不能因为某个玩家已经出过牌，就将他标记为本轮已响应并永久跳过。

只有当前最后成功出牌的玩家之外，其余三名玩家连续被检查且均不存在合法压制组合时，本轮才结束。

最后成功出牌的玩家获得下一轮领出权。

如果任何玩家打完手牌，立即结束整局，不再继续本轮。

## 8.1 状态机建议

至少维护以下状态：

- 当前桌面牌型。
- 最后成功出牌的玩家。
- 下一位需要检查的玩家。
- 连续无法压制的玩家数量。
- 当前整局状态。
- 当前牌权争夺轮次的唯一 ID。
- 房间状态版本。

每次成功出牌：

- 更新当前桌面牌型。
- 更新最后成功出牌玩家。
- 重置连续无法压制计数。
- 推进到下一位玩家。

每次无法压制：

- 自动跳过。
- 连续无法压制计数加一。
- 继续检查下一位玩家。

连续无法压制人数达到三人后，本轮结束。

本轮结束后，由最后成功出牌的玩家获得下一轮领出权，并重新应用适用的领出规则。

不要使用“每名玩家每轮最多行动一次”的状态模型。

# 九、手牌高亮与提示功能

## 9.1 手牌高亮

前端需要根据当前合法组合动态高亮手牌。

当玩家需要响应上家时：

- 枚举所有合法压制组合。
- 收集这些组合中涉及的实体牌 ID。
- 至少参与一个合法组合的手牌高亮。
- 不参与任何允许出牌组合的手牌置灰并禁止选择。

当玩家获得领出权时：

- 按领出规则枚举合法组合。
- 首局首次领出必须包含实体黑桃 3。
- 后续赢家首次领出必须排除被禁止的首手组合。
- 高亮和禁选结果同样由合法组合计算得出。

选牌过程中也必须进行约束检查。不能因为两张牌分别高亮，就允许玩家将它们拼成不合法的牌型。

## 9.2 提示按钮

点击提示后，按从小到大的顺序循环展示所有合法组合。

要求：

1. 第一次点击展示排序后的第一组组合。
2. 再次点击展示下一组。
3. 到达最后一组后循环回第一组。
4. 玩家可以选择提示的组合，也可以手动选择其他合法组合。
5. 提示结果不能绕过强制出牌和首出限制。
6. 当前桌面牌型改变后，重新计算提示候选列表并重置提示索引。

提示候选必须包含所有合法压制组合，包括普通牌型和炸弹。

不同牌型之间的统一排序规则尚未完全确定。请将组合排序实现为独立的 HintComparator，并在文档中列出需要确认的跨牌型排序问题。不要擅自认定炸弹永远排在最后或最前。

# 十、胜负与计分

## 10.1 整局胜负

最先出完全部手牌的玩家为本局赢家。

剩余三名玩家按剩余手牌数分为五档：

| 档位 | 剩余手牌数 |
|---|---|
| 1 | 1 张 |
| 2 | 2–5 张 |
| 3 | 6–9 张 |
| 4 | 10–12 张 |
| 5 | 13 张 |

档位 1 不输分、不赢分，但炸弹分另算。

提供至少两种可配置的计分方案：

| 档位 | 1-2-4-6 方案 | 3-5-10-15 方案 |
|---|---:|---:|
| 1 | 0 | 0 |
| 2 | 1 | 3 |
| 3 | 2 | 5 |
| 4 | 4 | 10 |
| 5 | 6 | 15 |

赢家获得其他三名玩家输分的总和。

不要把分值写死在业务代码中，应通过 ScoreRuleConfig 配置。

## 10.2 炸弹分

炸弹分独立于剩余手牌档位。

已确认规则：

- “2 炸弹”按档位 4 的分值计算。
- 其他炸弹按档位 3 的分值计算。
- 炸弹得分时，其他三名玩家分别支付对应分值。
- 炸弹打出后，分数需要立即体现。
- 同一轮中，如果该炸弹被更大的炸弹压过，被压过的炸弹不得分。
- 最终只有该轮最大的炸弹得分。
- 如果更大的炸弹再次被压过，则以最终最大的炸弹为准。

例如使用 1-2-4-6 方案：

- 2 炸弹：每名其他玩家支付 4 分。
- 其他炸弹：每名其他玩家支付 2 分。

建议实现独立的 BombScoreLedger，记录：

- 炸弹所属玩家。
- 炸弹牌型及比较值。
- 所属轮次。
- 当前是否为该轮最大炸弹。
- 已入账分数。
- 冲正记录。

炸弹打出时立即记账；如果之后被更大炸弹压过，立即冲正之前的炸弹分，并记录新最大炸弹的分数。

所有分数变化必须可以追溯，不允许直接覆盖历史记录。

“2 炸弹”的具体牌型构成和炸弹大小关系尚未完全明确。请通过独立的 BombPolicy 隔离，并在 open-questions.md 中标记，不能擅自决定其构成。

# 十一、后端架构与并发

第一版采用模块化单体。

建议拆分以下逻辑模块：

- 用户模块。
- 房间模块。
- 游戏规则引擎。
- 对局状态机。
- WebSocket 消息处理。
- 计分与结算模块。
- Redis 持久化适配器。
- MySQL 持久化适配器。

游戏规则引擎必须是纯 Java 模块，不依赖 Spring、Redis、MySQL 和网络层。

## 11.1 同一房间必须串行处理

每个 roomId 对应一个串行执行上下文。

同一房间中的以下事件必须有确定顺序：

- 玩家出牌。
- 自动跳过。
- 超时处理。
- 玩家断线和重连。
- 炸弹分记账和冲正。
- 本轮结束。
- 整局结束。
- 结算。

可以使用基于 roomId 的串行任务队列或等价的并发控制机制。

不要在同一房间内允许多个线程并发修改游戏状态。

## 11.2 服务端权威

客户端只能提交操作意图，不允许提交自己计算好的权威游戏状态。

服务端决定：

- 洗牌和发牌。
- 玩家当前是否有出牌权。
- 当前合法压制组合。
- 出牌是否成功。
- 当前桌面牌型。
- 自动跳过和回合推进。
- 游戏是否结束。
- 最终计分结果。

不能将其他玩家的完整手牌发送给当前客户端。

## 11.3 断线重连

实现：

- 玩家重新连接。
- 校验玩家身份。
- 恢复所属房间。
- 获取当前房间公开状态。
- 获取该玩家自己的手牌。
- 恢复当前桌面牌型、轮到谁以及剩余倒计时。

禁止将对手手牌、隐藏牌堆或其他不应公开的数据通过重连接口泄露。

超时后的行为尚未明确。请实现独立的 TimeoutPolicy，不允许简单地把超时等同于主动过牌，因为本游戏存在强制出牌规则。

设计统一的请求和响应协议，建议包含：

- 消息类型。
- 请求 ID。
- 房间 ID。
- 客户端操作序号。
- 期望的房间状态版本。
- 业务数据。
- 错误码。

至少支持以下业务事件：

- 登录成功。
- 创建房间。
- 加入房间。
- 玩家准备。
- 游戏开始。
- 发牌结果。
- 玩家出牌。
- 出牌成功。
- 自动跳过。
- 当前回合更新。
- 桌面牌型更新。
- 提示候选查询。
- 游戏结束。
- 炸弹分变化。
- 最终结算。
- 玩家断线。
- 玩家重连。

协议必须具备幂等性和状态版本校验能力，避免重复点击、网络重试或过期请求导致重复扣牌、重复结算。

# 十三、数据库与 Redis

## 13.1 MySQL

至少设计：

- 用户表。
- 对局记录表。
- 玩家对局结果表。
- 出牌记录表。
- 计分流水表。
- 炸弹分流水及冲正记录表。

为关键字段添加索引。

出牌记录应支持回放和问题排查，至少保存玩家、实体牌 ID、牌型、逻辑癞子身份、操作序号和对应状态版本。

## 13.2 Redis

用于：

- 玩家在线状态。
- 房间与游戏服务节点映射。
- 必要的对局状态快照。
- 断线重连辅助数据。
- 临时会话信息。

不要把所有数据都放 Redis，也不要把 Redis 当作不可恢复的唯一历史记录来源。

明确快照持久化、数据库事务和房间状态恢复策略。

# 十四、测试要求

测试是本项目的交付条件，不是可选工作。

## 14.1 规则引擎单元测试

至少覆盖：

- 单张和对子大小比较。
- 三不带、三带散、三带对。
- 牌型一致性。
- 最小顺子 12345。
- 顺子 23456 大于 12345。
- 连对 AA22、2233、3344 的顺序。
- 飞机 AAA222 和 222333 的顺序。
- 飞机带散与带对。
- 禁止混合飞机附件。
- 炸弹压制普通牌型。
- 炸弹不是强制优先出牌。
- 癞子参与所有受支持牌型。
- 赢家首手限制。
- 首局黑桃 3 必须包含在首手中。
- 非法牌型和非法癞子替代方式被拒绝。

对于未确认的特殊规则，应编写标记为待确认的测试，不要用猜测结果冒充已确认规则。

## 14.2 状态机测试

必须测试：

1. 玩家 1 首出，玩家 2、3、4 依次压制。
2. 再次轮到玩家 1，玩家 1 有牌可压，必须继续出牌。
3. 多名玩家连续多圈压制。
4. 某个玩家没有合法组合，自动跳过。
5. 新玩家成功出牌后，连续无法压制计数重置。
6. 当前最后成功出牌者之外的三名玩家均无法压制，本轮结束。
7. 本轮胜者获得下一轮领出权。
8. 有人出完手牌后立即结束整局。
9. 并发出牌请求不会造成重复扣牌。
10. 重复请求不会重复结算。
11. 炸弹被更大炸弹压过时正确冲正。
12. 最终只有本轮最大炸弹得分。

## 14.3 随机模拟测试

实现一个可重复执行的随机牌局模拟器。

要求：

- 固定随机种子，确保问题可以复现。
- 验证每张实体牌最多属于一个玩家。
- 验证牌张总数守恒。
- 验证任何出牌都来自对应玩家的手牌。
- 验证合法出牌后手牌数量正确减少。
- 验证自动跳过不修改手牌。
- 验证本轮结束条件。
- 验证计分总额满足既定结算规则。
- 发现异常时输出完整的牌局操作日志。

不要仅凭少量手工示例就认定规则引擎正确。
