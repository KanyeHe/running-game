# 架构和实现边界

模块化单体：HTTP/WS → RoomService → 纯 Java Game / CardCombinationFinder → StateStore。Java 25；Spring Boot 3.5.16。内存配置和持久化配置为不同 Spring Profile。

同一 roomId 使用同一 monitor 串行处理成员变化、准备、出牌、跳过、冲正、结算、重连和断线。网络回调仅提交意图。操作前复制已提交房间，操作成功后持久化，再广播；存储异常不把半完成状态写回内存。当前锁仅在单进程有效，Compose 只能部署一个 server 实例，Redis 节点映射不能代替分布式所有权。

每次状态修改推进房间版本。出牌同时推进 Game 版本；客户端提交房间期望版本。服务端重新生成合法候选，用稳定组合 key 精确验证实体牌集合、替代、牌型、首出限制和桌面压制，不接受客户端计算结果。

每位玩家操作 seq 必须递增；回执键 playerId+seq，校验 requestId 和请求内容。重复请求返回当前私有快照及原 acceptedVersion，不重复扣牌/记分；最近 512 个回执存快照，旧序列由高水位拒绝。广播中各连接只收到自己的手牌和候选，其余玩家只有手牌数。弃牌、全手牌、令牌、内部回执不投影给客户端。

持久化模式 MySQL 事务提交房间完整私密快照、对局/玩家结果、出牌事件、操作审计和积分流水。Redis 写入发生在 SQL 提交之后，缓存失败仍以 SQL 为准；恢复总是读 SQL。内存模式重启不能恢复；持久化模式新连接用原令牌恢复成员身份、手牌、桌面、牌权和绝对截止时间。

身份为 256 位随机令牌的游客会话，非微信正式身份。仅 AUTH 消息传递令牌，不放在 URL。HTTP/WS 开发来源用 ALLOWED_ORIGINS 配置。消息长度及 Validation 校验失败返回业务错误；内部错误返回 SERVER_ERROR。

当前尚无退出房间、房间过期清理、跨节点路由、心跳保活、生产级令牌轮换和微信登录；四人固定房间用于 MVP 联调。累计历史保存在 SQL；客户端结算显示当前局分数。超时策略保留扩展，默认等待，不会把超时当成过牌。
